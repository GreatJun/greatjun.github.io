REUSABLE GAME RUNTIME

프로젝트를 가로지르는 런타임 설계

Knit Block Loop, Toy Commando, The Living Fortress, Backpack Fight, FatCat에서 반복한 구조입니다. 장르가 달라도 수명·실행 순서·데이터 조립의 경계는 일관되게 유지합니다.

ARCHITECTURE 01 · SCOPE & FLOW

수명과 게임 흐름의 소유자를 분명히 둡니다.

App Root와 additive Scene Scope가 전역·장면 수명을 나누고, EntryPoint와 GameController·State가 생성부터 결과까지의 전이를 소유합니다.

App Root → Scene Scope → EntryPoint → Controller · State
Knit·Toy·Backpack: App/Scene Scope · Castle·FatCat: Controller/State 변형
ARCHITECTURE 02 · RUNTIME ORDER

한 프레임 안의 변경 순서를 중앙에서 통제합니다.

GameLoop가 World Delta 반영, System 실행, Command 소비, Controller·State Tick을 순서대로 호출해 등록·실행·결과 전달의 시점을 예측 가능하게 만듭니다.

World Delta → Ordered Systems → Command Queue → Controller · State Tick
Knit·Backpack·FatCat: Command · Toy·Knit·Backpack·FatCat: EventPipe
ARCHITECTURE 03 · DATA & PRESENTATION

콘텐츠 조립과 화면 표현을 게임 규칙에서 분리합니다.

CSV·JSON·ScriptableObject를 Registry·Factory·DI가 런타임 객체로 조립하고, Camera·World Root·UI Canvas는 별도 표현 계층에서 화면 비율과 좌표계를 처리합니다.

CSV · JSON · SO → Registry · Factory → Runtime Model → World · UI View
Toy: 무기·행동 · Knit: Feature · Castle·Backpack·FatCat: CSV/SO

03 · FRAMEWORK R&D

CoreForge

PERSONAL UNITY FRAMEWORK · v0.1.0 · WIP

이미 있는 도구를 다시 만들기보다, 도구 사이에 남는 조립 규칙을 패키지로 고정합니다.

라이브러리 하나로 해결되지 않는 초기화 순서·수명·실패·검증· Adapter 경계를 반복 사례에서 추려냅니다. 모든 기능을 범용화하지 않고, 여러 프로젝트에서 필요가 확인된 경계만 CoreForge로 옮깁니다.

WHY ANOTHER FRAMEWORK?

새 기능보다 반복되는 결정 비용을 줄입니다.

01 · CONNECT, NOT REPLACE

라이브러리를 대체하지 않습니다.

VContainer·UniTask·Addressables 같은 검증된 도구는 유지하고, 생성·비동기·리소스·해제의 연결 규칙을 계약으로 묶습니다.

02 · INDEPENDENT CORE

Core는 독립적으로 사용합니다.

Common·Pool·Resource·Data Core는 Module 없이 직접 사용할 수 있고, 상위 조립 계층을 역참조하지 않습니다.

03 · OPTIONAL MODULE

Module은 필요한 만큼 더합니다.

선택적 Module이 ConfigSO 조립·초기화 순서·구성 검증·역순 해제와 좁은 facade를 제공합니다.

IMPLEMENTATION MAP

현재 코드와 계획을 같은 무게로 보이지 않게 합니다.

구현 · 부분 · 진행

COMMON & PATTERNS

Result·Logging·Disposal과 State·Event·Command·Loop는 구현, DI와 Serialization 일부는 정리 중입니다.

구현

POOL · RESOURCE · DATA

직접 사용하는 Core API와 선택적 Module 조립을 구현했고, Resource 경계에서 Resources·Addressables를 연결합니다.

구현 · 부분 · 계획

INPUT & UNITY BRIDGE

Input Dispatch는 구현, Entity.Unity는 부분 구현이며 UI/MVVM 표현 구조는 계획 단계입니다.

계획

ADAPTERS & SCALE

VContainer·UniTask·서비스 Adapter, Persistence·Platform·Simulation·Jobs 경계를 순차적으로 설계합니다.

ENTITY RUNTIME R&D

왜 곧바로 DOTS로 가지 않는가?

MonoBehaviour와 GameObject는 제작·View 연결에 강하지만, 개체가 늘면 등록·조회·Update 순서가 흩어집니다. 전면 DOTS 전환의 이주·디버깅·협업 비용을 먼저 지불하지 않고, 필요한 통제 지점부터 분리해 복잡도의 값을 측정합니다.

WHY MANAGED FIRST

기존 제작 방식을 유지합니다.

GameObject와 Managed OOP의 Authoring·View 연결은 보존하고, Entity 등록·조회·Tick의 통제 지점부터 분리합니다.

WHAT IT BUYS

변경 시점을 한곳에 둡니다.

EntityID·exact-type Bucket으로 등록·조회를 중앙화하고, 자동 Tick 대상의 Add/Remove는 Delta로 분리합니다.

TRADE-OFF

범용 성능을 가정하지 않습니다.

Managed 비용과 exact-type 조회 한계를 인정하고, 병목이 확인된 데이터만 Jobs 또는 별도 Kernel 후보로 검증합니다.

  1. CURRENT · PARTIALEntityWorld

    EntityID·exact-type Bucket과 자동 Tick 대상의 Add/Remove Delta를 구현했습니다.

    QueryExact 구현 · 다형 Query 미구현
  2. PLANNED · NOT IMPLEMENTEDEntityWorld.Jobs

    병목 데이터만 Native Snapshot으로 분리하는 Schedule·Complete 경계를 설계할 계획입니다.

    Jobs / Burst 구현 없음
  3. PLANNED · NOT IMPLEMENTEDEntityKernel & Benchmark

    Lite-ECS/DOD 후보와 기존 방식을 같은 부하·CPU·GC·메모리·최악 프레임으로 비교할 계획입니다.

    DOTS 또는 Kernel의 우위를 전제하지 않음

CoreForge는 진행 중인 개인 R&D입니다. 구현·부분 구현·계획을 현재 코드 기준으로 구분하며, Jobs·EntityKernel·Benchmark는 아직 구현하지 않았습니다.
